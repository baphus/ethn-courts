# ETHN admin dashboard and booking read contract

Implemented read-only staff dashboard and booking search/detail API. No booking, payment, allocation, or other business writes are performed. Current ETHN schema is `ethn.bookings`, `ethn.booking_items`, `ethn.court_allocations`, `ethn.courts`, `ethn.payments`, and `ethn.proof_reservations`; legacy `src/lib/admin/bookings.ts` and Supabase tables are not valid ETHN data sources.

## Access and shared conventions

- Require enabled staff identity (`owner` or `staff`) on every route, using `getCurrentStaff` / `verifyStaffIdentity` and `staffPool` from `src/lib/admin/ethn-staff-server.ts`, consistent with `src/app/api/ethn/admin/payments/route.ts`. Owners are staff-allowed; no owner-only feature is needed for these reads.
- Use `adminResponse` / `adminError`; dynamic, uncached `GET`s, `Cache-Control: no-store` (verify helper behavior before relying on it). Unauthorized identity: existing 401/403 convention. Invalid query: 400 `INVALID_INPUT`; missing booking: 404 `NOT_FOUND`; unexpected DB errors stay errors, not empty results.
- SQL must be parameterized. Read as restricted `ethn_checkout`, not migration owner. Explicitly grant only required `SELECT` privileges and verify RLS policies/effective grants; no blanket schema/table access. Do not add `owner_hash`, `tracking_hash`, idempotency `result`, proof `object_path`, or any capability/token to query projections, DTOs, logs, or errors.

## Dashboard

`GET /api/ethn/admin/dashboard` → `{ operatingDate: "YYYY-MM-DD", counts: { held, pending, confirmed, completed, expired, pendingReviewOverdue }, recentBookings: BookingSummary[] }`.

- `operatingDate` is current Manila operating date, calculated with `manilaDateStr(new Date(dbNow - anchorMinutes))` using `ethn.settings.anchor_minutes`; dashboard counts use `bookings.operating_date`.
- `held` counts only live holds whose `expires_at` is greater than database time. `pending`, `confirmed`, `completed`, and `expired` count literal statuses on the current operating date; rejected is search/detail only. `pendingReviewOverdue` counts pending bookings whose earliest item start is at or before database time (overdue at/before play start), never based on `expires_at`; checkout expiry stops relevance on payment submission. It does not imply payment verified, booking confirmed, or slot released. Counts are read from one database-time snapshot. No revenue, collected-money, estimated-money, or legacy “approved” metric.
- Recent list: newest `created_at` first, stable tie-break `id DESC`, fixed limit 8 (or current design's explicit small fixed limit); fields only `{id, guestName, status, operatingDate, createdAt, total, itemCount}`. `total` is booked amount, not collected revenue; include only if UI labels it clearly as booking total. Omit if not needed.
- One aggregate query plus bounded latest-row query; the latter uses a bounded correlated item count. Counts represent bookings, not slot/item rows. Dashboard source currently redirects `/admin` to `/admin/payments`; retired legacy dashboard `src/lib/admin/dashboard.ts` uses obsolete status/table names and fabricated-in-scope revenue logic—do not port it.

## Booking search and detail

- Preserve `/admin/bookings` and `/admin/bookings/[id]` as UI paths, but retired `/admin/bookings` currently redirects to `/admin/payments` (`src/app/admin/bookings/page.tsx`). No ETHN endpoint currently owns that route. Proposed endpoints: `GET /api/ethn/admin/bookings?q=&status=&from=&to=&page=&limit=` and `GET /api/ethn/admin/bookings/[id]`. Implemented detail payment DTO is explicitly camelCase: `{id,method,status,claimedAmount,claimedReference,receivedAt,verifiedAt,collectedAmount,acceptedReference,reviewedAt,reviewReason,proofAvailable}`; timestamp fields are ISO strings or `null`. Detail reads booking, items, and payments in one read-only repeatable-read transaction. Avoid colliding with retired `GET /api/admin/bookings/:id` (specified 410 in `docs/ETHN-CUTOVER-API.md`).
- Search response `{rows: BookingSummary[], page, limit, total}`. Allowlisted status values only: `held|pending|confirmed|completed|expired|rejected`; empty means all. Optional strict `YYYY-MM-DD` inclusive operating-date bounds (`from <= to`). Bounded trimmed `q` (e.g. max 100 chars); search UUID exact, guest name/email/phone by escaped substring, and `tracking_code` exact/prefix only. Never accept tracking token/hash; rate-limit as appropriate, no-store, no query logging. Bound page/offset and page size (default 20, maximum 50), deterministic order `created_at DESC, id DESC`; parameterized SQL. Return total count only from same authorized filter set.
- Detail response has booking identity and contact fields for staff, status, operating date, created/expiry timestamps, booking total, items `{courtId,courtName,startsAt,endsAt,durationMinutes,hourlyRate,amount}`, and explicitly mapped payment records `{id,method,status,claimedAmount,claimedReference,receivedAt,verifiedAt,collectedAmount,acceptedReference,reviewedAt,reviewReason,proofAvailable}`. Payment timestamp fields serialize to ISO strings or `null`; raw database rows are never returned. This is staff-only sensitive data: no caching, redact in errors/logs, and UI must not expose publicly. Do not return owner/tracking hashes/tokens, object paths, idempotency payload, proof URL, or private proof data. Existing `GET /api/ethn/admin/payments/[bookingId]/proof` is signed-link gate; use it only for eligible attached proof and never bypass it.
- Include walk-in bookings and finalized exception-reviewed bookings naturally because search reads the same bookings/payments tables, without treating review as confirmation. Detail shows actual payment state and safe staff review metadata; never create/change allocations or money as a read side effect.

## Implementation verification

Implementation uses `staffPool`, staff verification and response/error helpers; all routes are dynamic/no-store. Focused DB test uses a fresh disposable PostgreSQL database through migrations `0001`–`0014` as restricted `ethn_checkout`, verifies role flags/effective grants, staff authorization, filter/pagination behavior, redaction, current operating date, live holds, pending start-time overdue rules, literal states, walk-in and exception reads, and missing IDs. Services issue read-only repeatable-read snapshots; no production DB, hosted migration, or browser verification used. Evidence and exact commands are recorded in `docs/checks/2026-11-21-admin-booking-read.md`.
