# Prepaid walk-in implementation and verification

2026-11-20. Local build, tests and schedule-only verification; no hosted migration or browser run.

## Changes

- `db/ethn/0013_walk_in.sql`: `payments` INSERT policy for cash and GCash walk‑in: status must be `accepted`, verified fields non‑null, cash has no reference, GCash has reference and merchant snapshot.
- `src/lib/admin/ethn-walk-ins.ts`: `createWalkIn`. Validates input; staff lock → settings lock → courts/hours → candidate holds → expiry → `resolveSchedule` (same as checkout) → inserted booking (confirmed), item, confirmed allocation, accepted payment, audit. No ownership token, idempotency, proof, outbox or customer tracking.
- `src/app/api/ethn/admin/walk-ins/route.ts`: 4KB JSON, origin guard; maps `SLOT_TAKEN`, `REFERENCE_TAKEN` → 409, schedule/rate/configuration errors → 400.

## Limits

- Hours‑row test fixture must match the selected operating date’s weekday; test inserts Sunday (UTC day 0) hours for a day in two days.
- No browser, hosted migration, or real Auth identity verification.
- Cash walk‑in requires the same merchant snapshot as GCash walk‑ins (existing settings merchant). If merchant blank, only cash allowed; service throws `NOT_CONFIGURED` for GCash.
- Exclusive lock order `courts → candidate holds → settings` matches checkout; same small‑venue serialization shortcut applies.
- No idempotency or payment‑proof handling; walk‑in is a one‑shot staff‑recorded prepaid confirmation.
