# Customer checkout API

`POST /api/checkout` creates a hold for the active ETHN customer booking page. Legacy UI and routes do not call it. Send JSON containing `ownerToken` (customer-minted random UUID v4 capability), `idempotencyKey`, `date`, `ranges` (`courtId`, UTC ISO `start` and `end`), `displayedTotal` and `displayedVersion`. Preserve the owner token and key for retries. Both first success and replay return 200. Never send rates or server time. Requests with an Origin must match the request URL origin. The existing per-process proxy limit is not a distributed abuse control; forwarded IP headers require a trusted proxy.

New holds return `intervalMinutes`, the grid interval used when creating the hold. Divide each item's `minutes` by that interval to count grid slots. Older saved responses and idempotent replays can omit it; clients should not infer it from current availability.

`POST /api/checkout/release` accepts JSON with `ownerToken` and `checkoutId`. A matching customer hold and its held allocations expire together. Repeating a successful release returns 200; a missing or mismatched checkout or one that is no longer held or expired returns 409. Release does not cancel submitted bookings, delete proofs or refund payments.

The booking page calls release only after the customer confirms **Leave checkout**. Refreshing instead restores the hold and payment progress from the same tab without extending the server deadline. Uploaded proof can be reused; a screenshot interrupted before upload may need to be selected again.

The original server hold deadline remains the payment and proof submission deadline. Submission locks the owned checkout before checking proof storage and decides timeliness under that lock; proof inspection has a five-second timeout and failure rolls back without extending the hold. A valid submission that acquires the lock before expiry keeps its slots while proof is checked. An expired submission can record existing evidence but cannot reserve a slot. Customers who already paid should not pay again; use the checkout ID and receipt to contact the venue.

After submission, Step 4 replaces the saved checkout draft with a same-tab receipt reference (`checkoutId` and submission key). `POST /api/checkout/receipt` accepts those as `checkoutId` and `submitKey` plus the existing `ownerToken`; the read is private, uncached, and requires the exact owned submission. Successful bookings return the current status, original court schedule and payment method, customer name and masked email, and tracking credentials. If no booking was created, only the Not booked outcome and checkout ID are returned. The separate status QR/link and code-plus-email lookup do not expose those customer details.

Configure `ETHN_DATABASE_URL` with the dedicated non-owner `ethn_checkout` login (or `ethn_checkout.<projectref>`); no legacy database variables are used. URI query parameters are rejected. Remote connections require `ETHN_DATABASE_CA_FILE` pointing to a trusted CA PEM file; TLS certificate and hostname verification remain enabled. Local plaintext requires both `ETHN_ALLOW_LOCAL_DATABASE=1` and a loopback hostname (`127.0.0.1` or `localhost`), and is disabled in production. Provision and audit the restricted role separately as described in `db/ethn/README.md`; a username check cannot prove role privileges.

Pool is lazy, limited to two connections per process, and has connection, idle, statement and query timeouts. Production serverless connection lifecycle and hosted TLS have not been measured or verified. Do not deploy until those, authorization, remaining workflows and legacy cutover are approved and tested.
